# HRGenius Fixes Tracker

## PART A: AUTHENTICATION (make it real and secure)
- [x] A1. Token types: add a "type" claim ("access" / "refresh") and a unique "jti" to every JWT. JwtAuthenticationFilter must reject any token whose type is not "access". The /auth/refresh endpoint must reject any token whose type is not "refresh".
  - Added type ("access"/"refresh") and UUID jti claims to JwtTokenProvider, enforced access token type in JwtAuthenticationFilter, and rejected non-refresh tokens in /auth/refresh.
- [x] A2. Server-side refresh tokens: create a RefreshToken entity + Flyway migration (id, jti or token hash, user_id, expires_at, revoked, created_at, replaced_by). Store only a SHA-256 hash, never the raw token. On refresh: validate against the DB, revoke the old token, issue a new one (rotation). If a revoked token is reused, revoke ALL tokens of that user (reuse detection).
  - Created RefreshToken entity, V9 Flyway migration, RefreshTokenRepository, SHA-256 token hashing, token rotation, and reuse detection revoking all sessions upon reused revoked tokens.
- [x] A3. Logout must revoke the refresh token in the DB and clear the cookie. Add "logout from all devices" endpoint that revokes all of the user's refresh tokens.
  - Implemented token revocation in DB upon logout, added /auth/logout-all endpoint to revoke all refresh tokens of the user, and verified via AuthControllerTest and AuthServiceLockoutTest.
- [x] A4. Access token expiry back to 15 minutes (configurable). Refresh token 7 days.
  - Configured default access token expiration to 15 mins (900000ms) and refresh token to 7 days in application.yml and JwtProperties with environment variable overrides.
- [x] A5. Frontend: keep the access token ONLY in memory (remove sessionStorage usage in auth.service.ts). Use provideAppInitializer to call /auth/refresh once on app start (withCredentials: true) so the user stays logged in after a page reload. Route guards must wait for this initial refresh to finish.
  - Stored access token strictly in-memory in AuthService, removed sessionStorage tokens, integrated provideAppInitializer for initial /auth/refresh with credentials, and made route guards await initialization.
- [x] A6. Interceptor: refresh only on 401, not on 403. On 403 show a "You don't have permission" message and do not log the user out. Ensure only one refresh call runs at a time and queued requests replay correctly.
  - Updated jwtInterceptor to refresh only on 401, show 'You don't have permission' on 403 without logging out, queue concurrent 401 requests during token refresh, and added vitest coverage.
- [x] A7. Cookie flags from config: secure=true and SameSite=Strict in prod profile; secure=false only in h2/dev. Cookie path must match the real refresh path (/api/auth).
  - Added CookieProperties and configured secure=true/SameSite=Strict in prod, secure=false/SameSite=Lax in h2 and dev with path /api/auth; verified with unit tests.
- [x] A8. Login security: return the same generic "Invalid username or password" message whether the user exists or not (no "remaining attempts" or "account locked" hints that reveal a username exists). Keep the lockout logic, return 401 for bad credentials and 423 (or 429) for a locked account. Add simple per-IP rate limiting on /auth/login (e.g., Bucket4j or an in-memory filter).
  - Enforced uniform 'Invalid username or password' on 401 bad credentials without username leakage, returned 423 on locked accounts, implemented per-IP in-memory LoginRateLimiter returning 429, and proved with unit tests.
- [x] A9. Password management: POST /auth/change-password (requires current password, strength rules: min 8 chars, upper, lower, digit, special). Add a forced "must change password on first login" flag on User; the frontend must redirect to a change-password page when it is set. Add an ADMIN-only reset-password endpoint that sets a temporary password and sets the flag.
  - Added must_change_password flag, password strength validation, change-password and admin reset-password endpoints, Angular change-password page with guard redirection, and unit/MVC/frontend test coverage.
- [x] A10. User accounts for employees: when HR creates an employee (or a candidate is hired), create a linked User with role EMPLOYEE and a temporary password (must-change flag on). Add ADMIN endpoints + an Angular "User Management" page to list users, enable/disable accounts, unlock accounts, and assign/remove roles. A disabled user cannot log in or refresh.
  - Linked User accounts created upon employee creation/candidate hire with role EMPLOYEE and temporary password (must_change_password=true), enforced disabled user rejection on login and refresh, added ADMIN user management endpoints in UserController/UserService, and created Angular User Management page with unit/MVC/vitest tests.
- [x] A11. /h2-console permitAll and frame options only in the h2 profile; never in dev/prod. Swagger available only in h2/dev profiles (or ADMIN-only in prod).
  - Restricted /h2-console and frameOptions SAMEORIGIN strictly to h2 profile, enforced Swagger access restricted to h2/dev (and ADMIN-only in prod), handled NoResourceFoundException, and verified with integration tests.

## PART B: AUTHORIZATION (role + ownership, enforced on the backend)
- [x] B1. Create a central CurrentUserService (or SecurityUtils) that returns the logged-in User, their Employee id, and their roles. Remove duplicated helper code (hasRole, getEmployeeIdForUser) from controllers and use this service.
  - Implemented CurrentUserService for centralized user, employee, and role resolution, replaced duplicated helper methods (hasRole, getEmployeeIdForUser, getCurrentEmployee) across LeaveController, AttendanceController, PayrollController, and PerformanceController, and added comprehensive unit test coverage.
- [x] B2. Fix IDOR in LeaveController, AttendanceController, and any other endpoint that accepts employeeId from the client: an EMPLOYEE may only act on their own employeeId; if they pass someone else's id return 403. ADMIN/HR_MANAGER may pass any id. MANAGER may pass only ids of their direct reports (reporting manager relation).
  - Enforced IDOR protection in CurrentUserService.getEmployeeIdForUser and controllers: ADMIN/HR_MANAGER can act on any ID, MANAGER can act only on self or direct reports, and EMPLOYEE can act only on self (throwing 403 AccessDeniedException otherwise). Added tests in CurrentUserServiceTest, LeaveControllerTest, and AttendanceControllerTest.
- [x] B3. Create a reusable authorization component (e.g., @Component("authz") with methods like canViewEmployee(employeeId), isManagerOf(employeeId), isSelf(employeeId)) and use it in @PreAuthorize SpEL expressions, e.g. @PreAuthorize("hasAnyRole('ADMIN','HR_MANAGER') or @authz.isSelf(#employeeId) or @authz.isManagerOf(#employeeId)").
  - Created reusable Authz component (@Component("authz")) with canViewEmployee, isSelf, isNotSelf, isManagerOf, canActOnEmployee, canAccessDocument, canApproveLeave, canAccessPayslip, and isNotificationOwner methods; integrated into @PreAuthorize expressions across controllers; verified with AuthzTest.
- [x] B4. Employees: GET /employees (list) -> ADMIN, HR_MANAGER, and MANAGER (managers see only their team). GET /employees/{id} -> HR/ADMIN, self, or that employee's manager. Salary/CTC, PAN, Aadhaar, bank details visible only to ADMIN/HR and self.
  - Scoped GET /employees to ADMIN, HR_MANAGER, and MANAGER (filtering to manager's direct reports and self), protected GET /employees/{id} via @authz.canViewEmployee, and restricted salary/bank/tax details to HR/ADMIN and self via EmployeeMapper.
- [x] B5. Documents: list and download only for ADMIN/HR or the document owner. Validate file type and size on upload, and never trust the client file name for the storage path (prevent path traversal).
  - Enforced document access and download scoping to ADMIN/HR and document owner, validated file types (.pdf, .png, .jpg, .jpeg, .doc, .docx) and 10MB size limit, sanitized original filenames, enforced UUID storage filenames, prevented path traversal in load and delete, and added DocumentServiceTest coverage.
- [x] B6. Leave approvals: a MANAGER may approve/reject only leaves of their direct reports; nobody may approve their own leave. HR/ADMIN may approve any.
  - Enforced @authz.canApproveLeave on POST /leaves/{id}/action and in LeaveService.processLeaveApproval, preventing self-approval and ensuring managers only action direct reports while HR/ADMIN can approve any non-self leave, with unit test coverage.
- [x] B7. Performance reviews: manager review only by the employee's manager; self review only by the employee; peer feedback cannot be given to oneself.
  - Enforced @authz.canSubmitSelfReview, @authz.canSubmitManagerReview, and @authz.canSubmitPeerFeedback on PerformanceController endpoints, added validation in PerformanceService preventing peer feedback for oneself, and verified via AuthzTest and PerformanceServiceTest.
- [x] B8. Recruitment, onboarding templates, payroll runs, holidays, audit logs, analytics company-wide: ADMIN/HR only (verify every endpoint). Analytics team view: MANAGER sees only their team.
  - Enforced ADMIN/HR_MANAGER PreAuthorize on candidate, application, and offer endpoints in RecruitmentController, onboarding templates in OnboardingController, holidays in AttendanceController, audit logs in AuditController, and restricted company-wide analytics/exports to ADMIN/HR while scoping manager analytics to their direct reports in AnalyticsService; verified with AnalyticsServiceTest and AnalyticsControllerTest.
- [x] B9. Notifications: a user can read/mark only their own notifications (check ownership on PATCH /{id}/read).
  - Enforced @authz.isNotificationOwner(#id) on NotificationController.markAsRead and added service-level AccessDeniedException in NotificationService when marking notifications of other users; verified with AuthzTest.
- [x] B10. Replace every "Access denied" BadRequestException with a proper AccessDeniedException -> 403. Add a JSON accessDeniedHandler in SecurityConfig next to the existing 401 entry point, and handle AccessDeniedException in the GlobalExceptionHandler, so the error format is consistent.
  - Replaced BadRequestException with Spring Security AccessDeniedException for unauthorized payslip access in PayrollController, added JSON accessDeniedHandler next to authenticationEntryPoint in SecurityConfig returning consistent ApiError JSON format, and updated GlobalExceptionHandler to return specific access denied messages.
- [x] B11. Audit every controller method: write a table in docs/SECURITY_MATRIX.md listing each endpoint, HTTP method, and who can call it (ADMIN / HR_MANAGER / MANAGER / EMPLOYEE / self / team). Every endpoint must have an explicit rule; nothing should rely only on "authenticated()".
  - Audited all 17 REST controllers across the application, added explicit @PreAuthorize / @authz rules across all endpoints, and generated comprehensive docs/SECURITY_MATRIX.md detailing allowed roles, ownership scopes, and parameters.
- [x] B12. Frontend: hide menu items, buttons and routes based on role (role guard on every protected route), but treat this only as UX; the backend checks are the real security.
  - Attached roleGuard to analytics, employees, recruitment, and audit routes in app.routes.ts, and added role-based template conditions (@if) in main-layout sidebar hiding restricted navigation sections while preserving strict backend enforcement.
- [x] B13. Security tests: for every rule in SECURITY_MATRIX.md add MockMvc tests using @WithMockUser or real JWTs proving: allowed role -> 2xx, wrong role -> 403, employee accessing another employee's data -> 403, manager accessing non-team member -> 403, no token -> 401, refresh token used as access token -> 401.
